# 持续集成与安装包

[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) 会在向 `dev`、`main` 推送代码，
或向这两个分支提交拉取请求时运行，也支持手动启动。文档与流水线修改同样触发检查，避免路径过滤让必需检查一直等待。

- 前端任务检查依赖安全公告、类型、单元测试、架构边界和生产构建。依赖检查使用公开公告源，包含开发工具，发现中危、高危或严重问题时失败。
- 自动运行在 Linux 上执行前端检查和原生锁文件公告审计。原生审计发现漏洞条目时失败，保留信息性警告；已知间接依赖警告记录在安全模型中。
- 手动选择 `full` 会增加四个浏览器测试分片和三个桌面平台的后端测试，Windows 还会检查原生上下文菜单与生成的第三方声明清单。失败诊断保留三天。
- 在 `main` 手动选择 `package` 会执行前端检查，并只构建所选平台的安装包；它不会运行完整浏览器和后端矩阵。如需这些覆盖，请对同一提交另行运行 `full`。

`dev` 是集成分支，仓库默认分支为 `main`。合并到 `main` 后，在 Actions → CI →
Run workflow 中选择 `full` 或 `package`；打包时选择 `main` 和所需目标，其他平台按需分别运行。

可选目标包括 Windows 64 位安装程序、Linux 64 位 `.deb` 和 `.AppImage` 包，
以及 macOS ARM64 和 Intel 两种 `.dmg` 包。在成功运行的流水线页面中下载
`vrykell-<target>-<commit>` 产物，保留期限为三天。每份产物对应构建使用的精确
提交。版本号取自仓库清单；升级时请同步 `package.json`、对应锁文件、
`src-tauri/Cargo.toml`、对应锁文件和 `src-tauri/tauri.conf.json`。

构建使用仓库中的依赖锁文件和项目打包入口，入口会在组装安装程序前准备原生
上下文菜单。打包配置会嵌入许可文件。安装包复制的平台库仍需按照
[许可说明](licensing.md) 核对。

流水线保存构建产物，不自动创建发布页或版本标签。目前未配置分发签名和公证
凭据。原生上下文菜单沿用现有的开发证书流程，这与应用分发签名独立。正式发布
签名安装包前请配置分发凭据。CI 不需要应用 API 密钥或用户凭据。

请保持私密漏洞报告启用并保护两个分支，要求 `Frontend checks` 和 `Native dependency advisories` 通过及拉取请求评审，禁止强制推送和分支删除。这些仓库设置独立于已提交的流水线文件。报告流程见[安全政策](../../SECURITY.zh-CN.md)。

发布安装包前，对构建使用的精确源码版本运行 `full`，在发布说明中记录该版本、目标平台、流水线运行、校验和及测试覆盖。无法确认源码版本的外部安装包不能描述为已验证构建。仅修改源码不会重新构建已有发布产物。
